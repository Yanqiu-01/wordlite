# 迭代路线（0.4.5 → 1.1.5）

22 个可安装版本，其中 4 个大版本：`0.5.0`（比对内核）、`0.6.0`（检索与自建库）、`0.7.0`（AIGC 内核）、`1.0.0`（报告界面）。每个版本都必须带自己的回归断言、自己的 APK 与自己的 release，禁止只改版本号。

命名沿用现有约定：功能加一版，修复加一位。

## 进度

已发布到 `0.5.3`（`versionCode 24`，`v0.5.3` 带可直接安装的 APK 与 release）。下面表里的条目按实际交付情况对账，与计划不同的地方写在每节末尾的"对账"里，不偷偷改验收标准：

- 0.4.x 三条已全部交付（0.4.5/0.4.6/0.4.7），另加 0.4.4 的排版修复。
- 0.5.0 交付了逐字长串与指纹带；**0.5.1 的"命中按文献聚合"没做**，那一版实际交付的是知网接入与十条检索路各走各路，来源榜挪到 0.5.4 做。
- 0.5.2 交付的是"连不上时把找过的路摊开"（当时排在这条上的事），`byEngine` 只到检索源一级，不是文献一级。
- 0.5.3 阈值标定已交付：`tools/detect-calibration.ps1` 可重跑，拐点与表格在 `docs/detection-calibration.md`，标定语料在 `tests/corpus/`。窗口长度与 winnowing 窗定在 n=7、w=12、三枚共通指纹，句级 Dice 从 0.60 降到 0.55。
- 0.6.0 的真正前提是先修检索覆盖：`EngineSettings.perEngine` 现在一个数兼两职（既是每页条数又是整轮入库配额），中文三库一次就回满 12 条，所以第一个窗口之后所有源都在发请求前被跳过——默认设置下一篇长文实际只检索了开头。这条不修，0.6.x 后面几条都是空谈。

- **WCopyfind 式带内桥接**（`RUN_BRIDGE_GAP`/`RUN_BRIDGE_PRECISION`）。D3 自己定的前置条件是大模型改写形状的

## 每个版本的固定动作

1. 先写回归断言，再写实现。
2. `pwsh tools/test-host.ps1` 全绿；动到界面或渲染的版本再跑 Robolectric。
3. `pwsh tools/build-host.ps1` 出 APK，`pwsh tools/release-version.ps1 -Version x.y.z` 一次完成升版本、提交、打 tag、开 release 并附上可安装 APK。
4. **每一版都要与微软原生 Word 再对一次版**（常驻职责，不许攒到"以后统一对"）：`pwsh tools/capture-device.ps1` 采手机侧真值 -> `pwsh tools/word-parity.ps1`（分页归属）、`pwsh tools/edge-parity.ps1 -Impl new`（两端对齐右边界）、`pwsh tools/line-break-delta.ps1`（逐行换行点），上标/下标对行高与分页的影响单列一行数字；结果与 `docs/edge-parity-baseline.md` 的基线逐条对比，进步退步都写进去。真值来自桌面 Word 16.0 的 COM 扫描（`tools/word-line-breaks.ps1`、`tools/word-justify-truth.ps1`），手机版微软 Word 的包是仓库根的 `base.apk.1`（`base.apk (1).1` 是 Word Lite 自己的包，别搞混）。

## 第二轮：1.1.4 → 1.3.4（20 版）＋ 四个大版本（2.0.0 / 3.0.0 / 4.0.0 / 5.0.0）

上一轮（0.4.5 → 1.1.3，22 版/4 个大版本）走完，判据与报告界面都有了实测基线。这一轮只干一件事：**每一条判据与每一个界面数字，都要能追溯到一次可重跑的实测**。所以每条验收都点名仓库里已经存在的回归套件或实测脚本，写"待实测"的地方就是这一版要产出的那张表，不预先承诺还没量出来的数字。

延续的规矩：每个版本一个真改动，自己带回归断言，自己出 APK，自己开 release。**禁止只改版本号。** 版本号单增：已发到 `1.1.3`（`versionCode 35`）；本轮起点是 `1.1.4`，终点的四个大版本按 `2.0.0 / 3.0.0 / 4.0.0 / 5.0.0` 排。每条的通用底线与上一轮相同：`pwsh tools/test-host.ps1` 全绿；改动若动到判据或检索，`tools/detect-calibration.ps1` 与 `tools/rewrite-robustness.ps1` 的 `ENGINE CURRENT` 那一行的变化量与噪声必须在 CHANGELOG 里同时报出，噪声只许降不许升（当前 0）；动到界面或渲染的再跑 Robolectric（`sh tools/build.sh && sh tools/test.sh`）。

### 前提与瓶颈（先写清楚，否则验收数字会被读成两回事）

- **AIGC 那台秤现在称不出方向。** 3.0.0 的标注语料到位之后（`docs/aigc-corpus.md`），第一次拿"真人逐字摘录"对"机器成稿"量区分度，换算成"机写应更高"的 AUC 只有 **0.305**，方向是反的；真人多作者那一档还破了零误报地板（`margin` +0.084 → **-0.056**，H2 有 1 句越线、撤掉双门槛后 6/20 段含过线句）。所以 3.0.1 换系数之前，报告里那个 AIGC 数字只能读作"机器腔倾向分"，不许读成占比，也不许在这批语料上做任何"AI 率下降"的结论。3.0.1 的硬前置补成两条：补齐 `docs/aigc-corpus.md` 第六节列出的商用模型档与多作者正文档，并把"AUC(真人, 机器) < 0.5 即判候选系数表不合格"写成标定台的硬判据。
- **AIGC 没有标注语料。** 3.0.0 之前所有 AIGC 数字都只能读作"真人句子摸到的上界 + 一条自指反证"：现在唯一可用的负例是真人句与它的同源改写，"改写后"与"AI 写的"在特征上同源，所以旧权重的 p99 0.468 既可能是安全余量也可能是没撞上真 AI 段的运气（`docs/aigc-calibration.md`）。3.0.1 的换系数验收完全依赖 3.0.0 的语料；语料不到位，3.0.1/3.0.3 就地停住，不许换成拍脑袋的系数交付。
- **中文三库只有摘要可比。** 检索页给的是题名 + 摘要，文库正文与查询窗口不在同一尺度（入库正文中位数 79 字，查询窗口 448 字），所以相似率是下限而不是估计值。知网匿名检索逐句自召回 1/4 是这一路的天花板；万方一轮只回 1 条题录、连续零新增就被判取尽；维普 `mfetch` 的 sessionid 活不过一次 HTTP 往返（`EngineProbe` 的维普自召回是 0/4）。这些不是"再调一次阈值就能过"的瓶颈，突破要靠 4.0.2 的全文渠道与自建库。
- **报告里的"重复率"与"改写率"是两个数加起来的，"改写率"单独不可引用**（`docs/rewrite-robustness.md` 已知不足第 4 条）。本轮任何把这两个数拆开口径的改动，都要先把 `CharLedger` 的独立相加与重叠记数一起改，否则来源榜与指标卡会各说一套。
- **"重复率 0.00%" 在拿不到可比对证据时是一句假话。2.1.2 已落地：`DuplicateEngine.Report.hasComparableEvidence()`（命中非空 / 检索侧入库过可比正文 / 自建库检索前有材料，三者有一才许印比率）接进 `markRetrievalGap`，排在"有没有取回候选"那条早退之前，可比正文 0 篇一律降级成未完成查重；诊断台 D（200 但零条目）、E2（9 源只 1 源答话）、F（候选全被零分闸门挡住）三场的 5 条断言随之翻面，29 套件全绿。当年的诊断：**** 诊断台（`tests/ZeroRateAudit.java`，报告 `artifacts/agent-chachong/zero-rate-audit.md`）实测：9 个源里只有 1 个答话、另外 8 个全灭，或者检索回了 200 但解出 0 条（反爬页与真零命中在代码里是同一个形状），落到的都是 `comparableCandidates=0` + `state=部分完成`，报告照印 0.00%。口径定死为：**分子分母都来自"真的比对过"的字符（`CharLedger` 现口径不变），但比对证据为空时不许出口百分比**，只许说"量不到 + 缺哪几源"。`docs/oss-algorithms.md` 第 37 行那条"可比对字数不足时禁止输出 0.00%"是要守的那一条；`CHANGELOG.md` 第 326 行"联网成功而确实零命中仍照实显示"只在候选非空时成立，两句话按这条口径各自收窄，不再互相打脸。落点：`DuplicateEngine.java:718`（零分闸门排在入库之前，导致"零候选"与"零命中"共用一个形状）、`844-848`（`everyConnectorFailed` 只数 `skipped`，200-但-零条目 不算失败）、`ApiWorkflow.java:243,310-329`、`ReportStore.java:194-196,207-208`。另：每源响应原文目前只在失败时留档，"200 但零条目"什么都不落，这是最硬的盲区——先落原始响应，再谈改判据。
- **抗改写判据瞎在一处：它按句子比，而抄袭常把一句长句拆成两句。** 新加的地板台（`tests/DetectionFloor.java`，2026-10-08）实测一段同义替换加子句换序的轻改写：整段的字符袋 Dice 0.772，已经过 0.72 那道地板；但判据读的是逐句，两半分别 0.522 与 0.634，后一半在 `bagReach` 0.683 就判死，连求交集那一步都没走到，整段 0 命中。决定性对照：把其中那一个 `；` 换成 `，`——零字符改动，只是那句不再被切成两句——同一段文字报 5 处命中、37/73 字 = 50.68%。所以这是**比对片段粒度**的问题，不是阈值松紧，去拧 `TextCorpus` 那三个地板（Dice 0.50 / 包含率 0.90 / 袋 Dice 0.72）治不了它。要动粒度必须按 `docs/detection-calibration.md` 的零误报预算把真人语料重测一遍（n=7/w=12/min=3 那条 0.0% 同源误报的尺是天花板），不许照抄一个窗口宽度交付；`DetectionFloor.KNOWN_GRANULARITY_BLIND_SPOT` 翻成 false 必须与那次重测进同一次提交。

- **`w:beforeAutospacing/w:afterAutospacing` 解析器不认，而它不是空操作。** `tests/samples/input-liu.docx` 里 63 处为 true（另有 22 处写 false），全在表格单元格内与 `before=100 after=100 line=300` 成对出现。受控样张实测：`=1` 时声明的 before/after 整个作废、换成 Word 自己的自动距（单元格内相邻段 32.6→44.4px，正文 27.2→39.4px），`=0` 与不写完全相同（`tools/word-spacing-truth.ps1` 的 tbl_plain / tbl_autospacing_on / tbl_autospacing_off / autospacing_body / autospacing_body_off）。要落地必须先量清"自动距按什么算"——13.8pt 这一个读数不足以定规则，不许照抄一个系数交付。
- **不预设实测目标值。** 本轮所有验收里没写数字的地方就是"待实测"；量出来比现值差，就按差写并回退或就地停住，不许改口径、不许换分母、不许拿"业界都这么做"顶。

### 3.0.0 / 4.0.0 的两个大门：把验收钉在实测上

3.0.0（AIGC 内核）按上一节 3.0.x 走，只补一句：语料不许再拿同源改写冒充 AI，公开数据集许可不许再分发的，仓库里只留派生统计量；出厂门槛写死——用真稿那份独立留出（493 句人写 / 262 句机器）量 AUC ≥ 0.85 且人类句子误判 ≤ 2/1000，达不到就只交模型和报告。

4.0.0（检索与自建库）新增两条 2026-10-09 实测出来的硬事实，验收要围着它们写：

- **公开检索口只到摘要，正文级不是靠调阈值能开门的。** 维普检索第一条命中就是这篇样稿本身（题名、哈工大、2024 全对），但它只回题名+摘要 1,987 字，与正文对应句整段袋 Dice 最高 0.536；万方给同一篇 1,001 字摘要，0.538；判据地板是 0.72。
- **匿名能拿到中文正文的实测只有一条路**：OpenAlex（`language:zh` + `open_access.is_oa:true`）→ `best_oa_location.pdf_url` 下 PDF。中文库 543 万条里 OA 29.1 万条；样稿题目 4 种检索式 34 条里 15 条带 pdf_url；实下 12 个成 4 个，单篇 700–1,345KB / 6,600–12,355 字；`cursor=<next_cursor>` 翻页实测连打 8 次全 200。两个现成 bug 堵着：`PaperSources.fullText()` 第一行就把 `.pdf` 链接丢了，`HttpTransport.MAX_FULL_TEXT = 512KB` 会把 700KB 起的 PDF 截断。判据本身是活的：拿一篇 OA 论文自己的 32 句导进自建库跑 `TextCorpus.match` 得 100.0% / 25 处命中。
- 拿不到的路也记下来，别再试第二遍：哲社中心 `readDownloadUrl` 与 `getMinioSign` 都回"请先登录"；维普 `qikan` 412 WAF；万方详情页所有 URL 回同一个 168,407 字节的 SPA 壳；Europe PMC 全文通道 12 次抓取全 0 字；CORE 无 key 时 200/429/500 随机；没有任何公开镜像能下到中文硕士论文全文。
- 4.0.0 的验收因此是：真跑一轮样稿能报出"可比正文 N 篇"且 N > 0（走 OA 全文或用户自建库，二者都要通），报告里带"把这篇下进自建库"的入口，并且把 app 的 PDF 取字量与 PyMuPDF 的差距（同一份扫描字体 PDF：1,846 字对 9,414 字）查清是解析漏字还是必须 OCR。

## 改动怎么进仓库（多人在同一棵树里干活时）

今天踩到的：几个分头干活的进程报过来的提交号，在这个仓库里 `git cat-file -t` 都找不到对象（例：报过来 8a40b42 / 222483f / 1d05c7f / 5f07990，本仓库 main 当时是 68beb77）。它们改的文件确实落在这棵树里（`git status` 看得见），但**提交没有落进来**——于是发版前的必跑测试跑的是一个不含这些改动的 main，报告里写的数也就没地方复核。

规矩：谁改的文件谁负责让它变成**这个仓库**里的一个 ref（分支或 main），并且把 `git log --oneline -1` 与 `git status --porcelain` 的原样输出贴回来。报上来的号能不能用，一条命令就能验：

```
git cat-file -t <那个号>
```

验不过就当它没提交。发版只从 `main` 走（`tools/release-version.ps1 -Isolated` 会开一棵 main 的干净副本），所以工作区里未提交的改动再多也不会被发出去——这是保险，不是省事：没进 `main` 的东西等于没做。

## 版本账（2.4.0 这轮对一次总数，免得各说各话）

GitHub 上现在 39 个 release（`gh api repos/Yanqiu-01/wordlite/releases` 实数，不是凭印象）：`v0.3.4` 到 `v2.6.8`。**43 个带可直接安装的 APK**，`v0.3.4` 那一个只挂了源码包（`wordlite-source-0.3.4.tar.gz`）——它是第一个 release，当时还没把出包挂上去，别把它算进"可安装"里。"至少迭代 20 个版本"这一条按 38 这个数已经过了；到 `v2.6.8` 是 44 个 release / 43 个可安装（`v0.3.4` 那一个只有源码包）。

"包括 4 个大版本"这一条有两种数法，都摆在这里：

- 这份文件开头那句话按"比对内核 / 检索与自建库 / AIGC 内核 / 报告界面"四件事算，得 `0.5.0`、`0.6.0`、`0.7.0`、`1.0.0` 四个。这四版确实各自换了一次内核，但按版本号看它们是 x.y.0，不是 x.0.0。
- 严格按主版本号数，只有 `1.0.0` 与 `2.0.0` 两个。

按严的那一条走：还缺两个主版本，就是上面已经定了验收的那两族。两族的验收都钉在实测上，不许靠改版本号发：

- 检索与自建库：样稿真跑一轮能报出“可比正文 N 篇”且 N > 0，而且必须由手机上那一版报出来；报告里带“把这篇下进自建库”的入口；app 的 PDF 取字量与 PyMuPDF 的差距查清（已结案：是解析漏字，不是必须 OCR，见 `docs/pdf-text-extraction.md`）。
- AIGC 内核：真稿独立留出 AUC ≥ 0.85、人类段落误判 ≤ 2/千段且分母 ≥ 20,000 段、机器段落召回不为 0；达不到就继续 `calibrated() = false`，App 里不印 AIGC 百分比。

**2026-10-09 把两族的号对调**：检索与自建库改挂 `3.0.0`，AIGC 内核改挂 `4.0.0`。理由只有一条：版本号只许单增，而这一轮前一族的验收当场过了、后一族还缺语料，那么先过的那族占较小的那个号。对调不改验收：前一族那三条一条不少，“必须由手机报出”这道口径照旧；后一族的判据一字未改。本文件里日期早于 2026-10-09、写着“3.0.0（AIGC 内核）”或“4.0.0（检索与自建库）”的那些行是当时的原话，保留不改，含义按上面两个标题读。

对调的依据是这一轮在 **2.6.8 正式包**上的真机读数（华为 CDY-AN90，`EAMUT20528011355`，代理 `127.0.0.1:7897`，同一份样稿，用时 72 秒）：

- `本次比对材料 44 篇（7 组）：自建库 · 正文 3 篇 · Crossref · 只有摘要可比 4 篇 · Europe PMC · 只有摘要可比 12 篇 · 国家哲社文献中心 · 只有摘要可比 1 篇 · arXiv · 正文 8 篇 · 知网（期刊与会议论文） · 只有摘要可比 12 篇 · arXiv · 只有摘要可比 4 篇`：**可比正文 11 篇**（自建库 3 + arXiv 8），验收要的 N > 0 成立。
- `检索覆盖 35/49 个检索窗口 · 15380/19967 字（77.03%）`；OpenAlex、Crossref、Semantic Scholar 这一轮全部被 HTTP 429 挡住，报告逐条写明 `代理 127.0.0.1:7897 答了 HTTP 429；直连 拒绝连接`。
- **相似率还是 0.00%（摘要层 0/314 句）**。这个数是下限，不是“这篇没重复”：能拿到正文的那 11 篇跟这篇样稿不同领域，中文那几路公开检索只回摘要。把 0% 变成有意思的数靠两件事：随包离线语句库（正在做，没网也能比）与自建库正文继续扩。

3.0.0 不是把 2.6.8 改个名：它要把这一族从“能报出 N > 0”推到“离线也能出数”，随包语句库与自建库抓取的干净度（已知读不出正文的链接不再重复下、容量满了给说明、读不出正文的那些是否该按摘要参与比对）就算这一族的活。

`4.0.0` 那条再加一道口径限制（2026-10-09 加，理由是真机读数一直比不过主机读数）："可比正文 N 篇且 N > 0"必须由**手机上的这一版**报出来。主机侧确实有过真数——`docs/retrieval-recall.md` 那张表里 可比正文 5 篇 / 6 篇、`fullText=5`/`fullText=6`，那是 2.3.0 时代在主机上直连跑的，正文来自开放获取那几路（europepmc / openalex 一族），不是知网、万方、维普。真机这边到 2.5.0 为止最好的读数是 `总相似度比 0.13%`、`检索覆盖 8/49 窗口 · 4188/19967 字`、`知网、万方、维普只回摘要`，也就是 N = 0。

这条在 **2.6.3 的真机上已经过了**：同一份样稿跑完整轮扫描报 "本次比对材料 50 篇（7 组）：自建库 · 正文 1 篇 … OpenAlex · 正文 7 篇"，`其中 7 篇抓到开放获取全文`，N = 8 > 0（2.6.2 那一次是 `OpenAlex · 正文 0 篇`，差在跟下载口那一次跳转）。验收条件按实测成立，但这一轮仍按修复版出包（2.6.4），主版本号留到检索与自建库这一族真正成规模再补。

`3.0.0` 照旧不达标，停在 2.x：段落级独立留出探针最好的只有 rank-average 三特征 AUC 0.8514、人类误判 1.81/千句（95% CI 0.96~3.44，分母 4,961 段）、机器召回 1.4%；更像产品的 49 段机器段落集上最好 0~2/49。发布的判据仍然 `calibrated() = false`，App 里不印 AIGC 百分比。数在 `docs/aigc-paragraph-scale.md`。手机没网口那阵子连这一行都出不来：十个检索源全部 `ECONNREFUSED`，`=> 0 of 10 open`，2.5.0 修的就是那条去路。

（2026-10-09 补一句：这一行里的 3.0.0 指 AIGC 内核那一族，现在挂 4.0.0；这一族的分母要求从这天起从 4,961 段提到 20,000 段以上，段落级留出正在扩。）

2.6.1 之后补一轮真机读数（2026-10-09，同一台华为 CDY-AN90，代理走 `127.0.0.1:7897`）：应用里点一次整篇查重，17 秒跑完，`检索自检 9/9 个源可用`、取回 48 篇候选、入库 36 篇、**可比正文仍是 0 篇**、`检索请求已达上限 120 次` 卡在 8/49 个窗口、"可以下进自建库的开放获取全文"从 10 条收窄成 4 条真链接。同一天用 `tests/android/EngineProbe` 在手机上按应用同一条检索与取文路径量，另一条查询能把可比正文推到 22 篇并第一次在本机看住一处 63 字的出处。两个数都算数，但 **4.0.0 只认前者**：验收写的是"样稿真跑一轮"，那就必须是应用那一轮的预算、窗口分配、全文名额一起把 N 顶过 0，卡在 120 次请求上的那一轮不算过。

发版还有一条流程账（2.6.0、2.6.1 两版踩出来的）：工作树常常是脏的（好几个改动并行），所以发版一律在 `origin/main` 的一棵副本里做，要并进来的本地提交用 `git merge`，不许用 `git cherry-pick`——挑过来的提交换了父提交，本地 `main` 就再也快进不了 `origin/main`，下一版从哪儿切就乱了。副本拆掉之前先把 APK 与校验和搬回主工作区（`tools/release-version.ps1` 里 2.6.0 那一次把这段写在拆副本之后，条件永远不成立，本地一份包都没留下，装机得从 GitHub 往回下 202 MB）。

断点一致率的口径也定死一条（见 `tools/break-agreement.ps1` 与 `tools/word-line-breaks.ps1`）：以 Word 自己导出的 PDF 逐行读回的 356 行为真值，起点 28.5%（100/351），报数必须带那条 sha。旧口径 69.7%（对我们自己的行序量）只作对账，不许与新数并列。排版这条线的优先级固定：页数与页归属 > 断点率 > 行高。
