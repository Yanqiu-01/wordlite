# 抗改写召回实测台

`tools/test-host.ps1` 里的 `RewriteRobustnessRegression` 测一件事：**把一段真论文抄进稿子、再用某种口径改写过之后，
还有多少字会被标成重复**。0.7.3 的端到端召回实测台（`docs/retrieval-recall.md`）证明逐字复制那一头瓶颈在检索不在
匹配，这条断言只覆盖了逐字；改写那一头当时没有任何数字，只有"句级 Dice 0.55 应该扛得住一般改写"这种话。

## 口径

从 `tests/corpus/real-prose.txt`（真人写的论文正文，每行一段）里挑出有效字符不少于 120 的段，
**先用本应用自己的引文判据 `TextCorpus.citationLike()` 把参考文献条剔掉**（这一步是实测逼出来的，见下面"噪声"那一节），
剩下的段按奇偶分两拨：

- 偶数段进文献库，一段算一篇（`PAPER-0…PAPER-19`，共 20 篇 4567 字），它们同时也是被抄的段；
- 奇数段**永远不进库**，只当稿子里学生自己写的话，夹在被抄段之间。

稿子按"自己写一段 → 种入一段"交替拼出来，每个种入段在原稿上的区间和它应有的出处都记着。跑一遍真的
`TextCorpus.match()`，量三件事：

| 指标 | 算法 |
| --- | --- |
| 召回 | 种入段里被命中区间盖住的有效字符 / 这段的有效字符 |
| 归属 | 其中记在真正出处名下的字符 / 被标记的字符 |
| 噪声 | 那些没进库的段落被标成的字符数 |

命中区间互不重叠是 0.7.3 之后 `match()` 的结构性保证，实测台每条口径都重新数一遍相交对数，不为零直接抛
（`measure()` 里），因为一旦重叠，"盖住多少字"就会双算，整张表跟着作假。

噪声这一列是这台机器的关键。只报召回的实测台可以靠把阈值放松刷出任何好看的数字，所以每一行都必须同时给出
误报，而且实测台自己要先证明它看得见误报：`floors()` 里有一条断言把阈值压到 0.30 再测一遍，**必须**撞出误标来，
撞不出来就说明前面那一串零是瞎出来的。

## 十五种口径

全是确定性变换：同一份输入永远给同一份输出，不含随机数、不联网，所以能进闸门。

| 口径 | 做法 | 是不是真实降重写法 |
| --- | --- | --- |
| `verbatim` | 原样照抄 | 对照组 |
| `app-rewriter` | 本应用自己的离线降重 `LocalRewriter`，逐轮采纳第一条建议，采纳到没有为止 | 是，而且是产品自己那一头 |
| `synonym` | 24 组同义词/连接词整词替换（例如→比如、因此→所以、采用→使用…） | 是 |
| `clause-order` | 句内分句倒序（"因为 A，所以 B"→"所以 B，因为 A"） | 是 |
| `sentence-order` | 段内句序倒序 | 是 |
| `number-style` | 数目字写法互换：`12.5%` → `百分之十二点五` | 是，也是最常见的录入差异 |
| `drop-20pct` | 每五句丢一句 | 是 |
| `stacked` | 离线降重 + 分句倒序 + 丢两句 | 是 |
| `pruned` | 只留偶数位的分句：抄来的内容被抽稀成互不相邻的碎块 | 半真，专门打 18 字的指纹带 |
| `split-commas` | 句中每个逗号改成句号（拆句） | 是，降重手册上最便宜的一招 |
| `merge-pairs` | 相邻两句并成一句 | 是 |
| sub-char-10/25/50 | 每 10/4/2 个汉字换一个 | **不是**：逐字替换比任何真实同义替换都狠，用途是量容忍度曲线而不是模拟人 |
| local-edit-16/25 | 每 25/12 个汉字整块换掉 4/3 个连续汉字 | 半真：改动率和逐字替换可比，但空间分布是"几处疤"而不是"均匀铺开"，这才是 LLM 改写与大段誊抄的真实形状 |
| `spliced` | 上句的头接下句的尾，跨句拼接 | 是 |

## 实测（0.7.4，`SIMILAR_DICE = 0.50`）

20 段种入、85 句同领域负例，一轮 15 条口径：

| 口径 | 种入字数 | 标记字数 | 召回 | 归属 | 噪声 | 改动字数 |
| --- | --- | --- | --- | --- | --- | --- |
| verbatim | 4522 | 4513 | 99.8% | 100.0% | 0 | 0 |
| app-rewriter | 4518 | 4509 | 99.8% | 100.0% | 0 | 291 |
| synonym | 4517 | 4508 | 99.8% | 100.0% | 0 | 691 |
| clause-order | 4522 | 4515 | 99.8% | 100.0% | 0 | 3523 |
| sentence-order | 4522 | 4513 | 99.8% | 100.0% | 0 | 4336 |
| number-style | 4570 | 4570 | 100.0% | 100.0% | 0 | 2770 |
| drop-20pct | 3857 | 3848 | 99.8% | 100.0% | 0 | 1308 |
| stacked | 3856 | 3849 | 99.8% | 100.0% | 0 | 3965 |
| pruned | 3055 | 2987 | 97.8% | 100.0% | 0 | 3805 |
| split-commas | 4522 | 4493 | 99.4% | 98.8% | 0 | 197 |
| merge-pairs | 4523 | 4508 | 99.7% | 100.0% | 0 | 65 |
| sub-char-10 | 4522 | 4513 | 99.8% | 100.0% | 0 | 332 |
| sub-char-25 | 4522 | 1194 | 26.4% | 100.0% | 0 | 848 |
| sub-char-50 | 4522 | 76 | 1.7% | 100.0% | 0 | 1708 |
| local-edit-16 | 4522 | 4500 | 99.5% | 100.0% | 0 | 450 |
| local-edit-25 | 4522 | 4513 | 99.8% | 100.0% | 0 | 713 |
| spliced | 3040 | 3026 | 99.5% | 100.0% | 0 | 3328 |

四条立刻能用的结论：

1. **删和换序几乎不打不动这把尺子。** 丢两成句子、句序倒序、分句倒序、跨句拼接、并句，召回全在 97.8% 以上。
   原因是句级比的是三元组 Dice 与包含率：删掉的句子不在稿子里（不进分母），换序只打断跨在切点上的那两三枚三元组，
   而"抄来的半句整段嵌进改写过的长句"这一类由包含率那条路兜住。
2. **换字才是真正的悬崖。** 换掉一成汉字召回还是 99.8%，换掉两成掉到 26.4%，换掉一半只剩 1.7%。
   三元组重合度约等于 `(1-s)^3`，Dice 下限 0.50 折回替换率就是 `1 - ∛0.50 = 20.6%`——悬崖的位置和算式对得上，
   不是玄学。同理 0.55 那一档的容忍上限是 18.1%。
3. **数字写法不参与制造悬崖。** `number-style` 是唯一一条召回 100% 的改写口径，因为 `Fingerprints` 早把连着的
   数目字折成同一枚 token。0.55 时代这一条是 99.5%，降到 0.50 之后补齐。
4. **同样多的字，改动分布决定生死。** 换掉 450 字、集中在每句几处 4 字块里（local-edit-16），召回 99.5%；
   换掉同样量级的字、均匀铺在整段上（介于 sub-char-10 与 sub-char-25 之间），召回从 99.8% 一路掉向 26.4%。
   原因是 n-gram 只数连续重合：整块替换只在疤周围毁掉 块长 + n - 1 枚三元组，长段原文照抄的部分整段活着；
   均匀替换让每一枚三元组都带着 1-s 的概率被打散。**结论对产品的意义很大：真实降重（局部换词、调序、并句、删句）
   打不动这把尺子，能打动它的只有把全文每个词都换一遍那种改写，而那已经不是"抄"而是照着重写。**
5. **本应用自己的离线降重太温和。** 20 段一共只改动 291 字（每段约 15 字，全文的 6%），因为规则刻意让数字、
   单位、型号、术语整个活着——那是对的（改了术语就不是降重是改错），但也意味着降重功能实际推动的改写量很小，
   `app-rewriter` 这一行离 `verbatim` 几乎没有距离。这条差距记在 ROADMAP，不在匹配这一头解决。

## 阈值扫描（`-Drrs=1`）

同一份稿子、同一个库，只动 `diceFloor`，召回与噪声一起报：

| dice | 噪声 | sub-char-25 | pruned | split-commas | spliced |
| --- | --- | --- | --- | --- | --- |
| 0.55 | 0 | 19.2% | 96.2% | 98.1% | 99.3% |
| 0.50 | 0 | 26.4% | 97.8% | 98.1% | 99.5% |
| 0.45 | 0 | 31.3% | 99.4% | 97.1% | 99.7% |
| 0.40 | 0 | 46.1% | 99.4% | 97.1% | 99.7% |
| 0.35 | **399** | 66.5% | 99.4% | 97.1% | 99.7% |

包含率那一列（0.90/0.80/0.70）在这台机器上逐位相同，和标定台当年的观察一致：能配上的句子长短本来就接近。

**0.55 降到 0.50 的理由与边界。** 当年留 0.55 的话是"0.50 与 0.55 实测逐位相同，多留一档余量给真实文库"，
那句话在原文与常规改写的样本上成立，在逐字替换的样本上不成立：同一批 20 段、同一批 85 句负例，
两成替换那一档差 7.2 个点，分句抽稀差 1.6 个点，而两边误报都还是零。标定台在现行代码上重跑过，
`ENGINE CURRENT` 与 `dice=0.50` 那一行逐位相同（召回 99.5%、误报 471 字、`dupChars=3634`），
说明这一改在原六种写法上一笔未动，只在重写口径上多认回字。

**为什么停在 0.50 而不去 0.45**：0.45 还能再多认回约 5 个点，但下面那张分布表显示这批负例能摸到的最高
Dice 是 0.358，0.50 头顶还有 0.14 空档，0.45 只剩 0.09；文库上了几千篇几万篇规模之后偶发撞车要吃的正是这一档。
哪天真实文库规模够大、负例天花板仍压在 0.36 以下，再往 0.45 走，走之前先把这张表重跑。

## 漏掉的字卡在哪一层（`-Drrroc=1`）

把阈值临时压到近零，让每个句子都把"库里最像的那一条"报出来，漏检的原因就分得开了：分值堆在 0.45~0.55 之间
是阈值卡住的，分值正好是 0 的是**压根没问到候选**。

`sub-char-25` 的 83 句正例：`=0` 零句、`(0,0.3]` 10 句、`(0.3,0.4]` 37 句、`(0.4,0.45]` 12 句、
`(0.45,0.5]` 3 句、`(0.5,0.55]` 6 句、`>0.55` 15 句。**阈值那一头最多只能捞回 9 句**，剩下 45 句压在 0.45 以下，
不是调阈值能解决的——那需要词序无关的特征（词集/语义），不是 n-gram 家族能做到的事。

按句长分桶再看一次，顺便否掉了一个顺手就能想到的方案：

| 句长 | 负例句 | 负例最高 Dice |
| --- | --- | --- |
| <20 | 1 | 0.158 |
| 20-35 | 8 | 0.179 |
| 35-50 | 21 | 0.152 |
| 50-80 | 40 | **0.358** |
| ≥80 | 15 | 0.162 |

"长句证据多、所以长句可以把下限放松"这个说法在这批样本上不成立：负例能摸到的最高分恰恰出现在 50-80 字的
长句桶里，短句桶反而 lowest。**长度加权的方向和直觉相反，所以这条方案不做。**

归属那一头有两个数字值得记：`sub-char-25` 换掉两成字之后，最佳候选**指对正确出处**的字符仍然是 4522/4522——
排序全对，只是被阈值挡在门外，这进一步说明要动的是判定线不是候选生成。而 `split-commas` 只有 1705/3937，
196 个碎片里 93 个连候选都没问到：包含率那条路的可达区间是长短比 1.6 到 3.0（`dice >= 0.5` 这一条自己把
比值上限卡在 3.0），拆出来的 16 字碎片对 54 字原句是 3.4 倍，结构上就进不了那条路。

## 一条被顺手挖出来的口径错误：抄得更多，报得更少

给拆句放宽包含率通道（长短比 3.0 → 4.3）之后，`split-commas` 从 98.1% **掉到** 92.8%。放宽一条判定线反而少认字，
只可能是判据之间互相咬。逐条打出来看是这里：**指纹带只补句级命中没盖住的字符，而"补不出最短可报告长度就丢掉"
这一刀是逐块量的**。一条 40 字的连续复制，中间被一句句级命中咬掉 8 个字，剩下两块各 16 字，两块都够不到
`MIN_MATCH = 18` → 全丢。于是句级命中越是先咬一口，带子能报出来的越少。

改成按"这条带子还剩下多少字"判：总长够 `MIN_MATCH` 就把剩下的每块都留下，归属与分子照旧走同一次并集。
理由不是"多报一点没关系"，而是证据本来就是这条带子——winnowing 保证的连续重合，被句级命中咬掉一段
并不会把剩下的字变成巧合。改完之后 `split-commas` 99.4%、`pruned` 不变、噪声仍为 0，标定台那一头
`ENGINE CURRENT` 逐位不动（召回 99.5%、误报 471 字、`dupChars=3634`、命中 60 条），PAIR / CROSS 误报仍是 0.0%。

那条被回滚的放宽实验留在这一段里，因为它是这台实测台唯一一次自己抓到自己：没有它，这个分块错误还会在
判据里躺很久，而它平时表现成的样子是"某些拆过句的段落就是不红"。

## 嵌入改写：抄进去一句 22 字，报出来整句 90 字全红

上面那次放宽还暴露了另一件事，而这件事这台机器以前**看不见**：包含率命中记的区间是**整个片段**，
不是实际共享的那一段。于是单独加一档 `embedding`——把库里某篇的一句短句整块嵌进一句学生自己写的长句里：

| 量 | 实测 |
| --- | --- |
| 嵌进去的那段 | 778 字，标了 716 字 = **92.0%**（该认的认回来了） |
| 它外面的自写文字 | 1578 字，被连带标了 688 字 = **43.6%** |

也就是说抄一句进去，句子外面自写的部分有将近一半跟着一起红。这一档之前没有任何一台机器量过它：
标定台的 `MARGIN` 只量 Dice 一条路，`docs/detection-calibration.md` 的"还没解决的"里那条
"长短悬殊的嵌入改写没进这批样本"说的就是它。

这个数字现在以**天花板**的形式钉在闸门里（平均每句连带标红不许超过 45 字），不是达标线：等包含率的命中
落到实际共享区间（`docs/ROADMAP.md` 1.1.1），它应该一路掉到个位数。顺序不能反——先把包含率通道放宽，
多报的那一头只会更大，这正是上面那次回滚量出来的代价（多报 3 倍，26 字的复制报成 85 字）。

## 落点裁到实际共享那一段：每句 41 字掉到 0 字，代价是四段拼接少认 4 字

1.1.1 改的就是这条落点。判据一个字没动，改的是命中记在哪一段：`SharedBlocks` 在折叠后的比较键上做二分公共块长度 + 滚动哈希求最长公共块，找到之后往两端各自扩到极大，再在剩下的左右区间里找下一段，一个片段最多 16 段；每段开销 `O((n+m)·log min(n,m))`，不建 n×m 的 DP 表，临时表逐句复用。两端再剥掉标点与符号才折回原文偏移——学生自己敲的那枚逗号常常正好对上文库那句里两个分句之间的逗号，字符串层面确实相同，可 `validCount` 认它为一个有效字符，不剥就是一枚凭空多出来的红。

| 量 | 裁之前 | 裁之后 |
| --- | --- | --- |
| 嵌进去的那段 | 723/778 = 92.9% | 720/778 = **92.5%** |
| 它外面的自写文字 | 681/1578 = 43.2%（每句 40 字） | **0/1578**（每句 0 字） |

（这两行是夹具窗口修正之后的数：`phraseStart` 原来多算一个字符，17 句逐句 `indexOf` 复核每句都差 1。上面那行 92.0% 是旧窗口口径下量的，裁前裁后必须用同一个窗口比。）

多报从 681 字掉到 0 字，只裁回来 3 个字。代价在哪：

- 丢的 3 字来自 1 句（probe 16，PAPER-19）。抄进去那句以序号 `1）` 开头，而入库那侧 `skipPrefix()` 会把序号前缀剥掉，两边的折叠串在这 3 个单位上本来就不相同——共享块不可能诚实地从更早的位置开始。其余认回来的句子，命中区间与被抄区间逐字相等（`[12,40)`、`[277,337)`、`[393,470)`、`[519,618)`）。
- `merge-pairs` 4508 → 4504（99.7% → 99.6%）、`spliced` 3026 → 3024。原因是同一个片段里有两句都过了线（同篇相邻两句、或两篇各一句）时，只裁进赢的那一句会把另一句连证据一起藏掉。于是加了守卫：**只有一个片段恰好只跟一个候选对得上时才裁**，多候选的片段整段报——抄两段只报一段比多报更糟。这条守卫同时把 `TextCorpusRegression.merging()` 顶了回来，那条钉的是「合并区间要盖住第一个到最后一个重复字符」，它不是可以改写的措辞。
- 17 句里另有 3 句（54 个有效字符）裁之前裁之后都没有命中，与裁剪无关：`LENGTH_BOUND_FLOOR = 0.5` 把这条通道的长短比封顶在约 3.0 倍，那三句的 gram 比是 6.6 / 4.9 / 3.5。那是 1.1.2 的活。

标定台 `ENGINE CURRENT` 在改动前后逐位不动（`recall=99.5% fpChars=471 dupChars=3634 hits=60 boilerplateShare=17%`）：这份真人语料里没有嵌入几何的命中，所以这次改动在真实论文上的第一层影响是「不变」，它搬动的只有嵌入与拼接这两种形状。闸门里的天花板从每句 45 字收到 4 字（实测 0）。

还没跟着改的：`hit.score` 仍是那一对片段的加权 Dice，不按裁后区间重算，所以一条窄命中的分值说的可能还是整个片段的相似度；`MIN_SHARED_BLOCK = 5` 与 `MAX_SHARED_BLOCKS = 16` 只在宿主用例上定过，没在真文档标定台上扫过。
## 噪声那一节：参考文献条是自己人打自己人

第一版实测台没有 `citationLike` 过滤，噪声一列全是 1149 字，逐条打出来看全是这种东西：

```
NOISE chars=24 score=0.667 source=PAPER-24 :: 2024, 39(10): 13471-13486.
NOISE chars=20 score=1.000 source=PAPER-1  :: Transient Liquid Phase
NOISE chars=20 score=0.772 source=PAPER-25 :: 2020, 10(7): 934.
NOISE chars=148 score=1.000 source=PAPER-36 :: Novel Transient Liquid Phase Bonding through C
```

参考文献条互相判重是**真实存在**的行为：同一本刊名、同一个 `et al.`、同一副英文题名在文档里出现两次，
逐字重合当然高。它算不算冤枉要看场景——同一份文献表里同一条列两遍是真重复，而"稿子里的参考文献表"本来就该由
`TextCorpus.structure()` 的参考文献区识别整体退出比对。实测台把正文和参考文献混在一起测，只会把正文那一列的噪声
数字弄脏，所以现在用应用自己的 `citationLike()` 先把 38 行进库位、若干行负例位剔掉。这条行为差异记在这里，
是为了防止下一次有人拿参考文献的分数当误报率。

## 已知不足

- `sub-char-*` 是逐字替换，不是任何真实改写工具的输出；它能定容忍度的上限和悬崖位置，不能当成"某某降重软件
  改过的稿子我们能认回多少"。真实第三方改写工具的量级没有测过，因为没有可复现的第三方工具输出可喂。
- 文库是**同一篇论文的 20 段**，负例是同一篇论文的 65 句正文。同领域同源，术语全撞车，这是诚实的负例，
  但它代表不了几千篇文库下的偶发撞车；天花板数字（0.358）只在这一批样本上成立。
- 种入粒度是段，命中粒度是句，所以"半句抄、半句自己写"这种句内混合没有单独一档口径；`pruned`/`spliced`
  是它粗糙的替身。
- AIGC 判定与这台机器完全没有关系，别拿上面任何一张表当 AIGC 的标定物（那边仍然缺带标注的人写/机写语料）。
